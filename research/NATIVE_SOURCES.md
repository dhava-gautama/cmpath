# Native implementation choices and next measurements

Sources accessed **2026-09-11**. This note distinguishes implemented Go paths from an unimplemented Rust alternative. It supplements the local protocol and results; upstream documentation establishes capabilities and constraints, not CMP performance.

| Path | Concrete integration and deployment consequences |
|---|---|
| Embedded Go API — implemented | A Go host imports `native/engine` and calls it in process, avoiding the JSON/stdio boundary. This is source-level Go integration. Exporting a library to other languages would require a separate ABI design: Go's `c-archive` and `c-shared` modes expose functions explicitly marked for C export, not arbitrary Go package methods. The current project does not provide that shared-library interface. [Go build modes](https://pkg.go.dev/cmd/go#hdr-Build_modes) |
| Go plus bundled SQLite through cgo — implemented | Direct Go embedding still calls SQLite's C implementation. cgo needs a C compiler; cross-compilation requires an appropriate target C compiler and enabling cgo. Pointer retention and ownership must obey Go/C rules, and string conversions can copy and allocate. This is not a pure-Go build. [cgo documentation](https://pkg.go.dev/cmd/cgo) |
| Rust plus rusqlite — possible, not implemented | rusqlite wraps SQLite's C API through `libsqlite3-sys`. Its optional `bundled` feature compiles SQLite with the `cc` crate and links it, avoiding reliance on the installed SQLite version while retaining C-toolchain requirements. Default library discovery uses tools such as pkg-config or vcpkg. A Rust rewrite would therefore not replace the underlying database algorithm by itself. [rusqlite build documentation](https://github.com/rusqlite/rusqlite#notes-on-building-rusqlite-and-libsqlite3-sys) |
| Rust plus PyO3 — possible, not implemented | A native Python extension would remove this project's subprocess transport, while adding Rust/Python FFI and wheel distribution work. PyO3 supports `cdylib` extension builds; stable-ABI options can reduce Python-version wheel variants but still require OS/architecture builds and restrict available optimizations. Free-threaded Python compatibility needs an explicit ABI/build choice. No Rust speed result or working Rust backend is claimed here. [PyO3 building and distribution](https://pyo3.rs/main/building-and-distribution.html) |
| Persistent Python-to-Go stdio bridge — implemented | Python launches a separately distributed native executable and exchanges framed JSON while it stays alive. This avoids a CPython extension ABI dependency but requires executable selection, pipe handling, timeouts and process-lifetime management. Persistence amortizes startup; encoding, copies and IPC remain per operation. Python documents the risk of blocked subprocess pipes when outputs are not drained. [Python subprocess documentation](https://docs.python.org/3/library/subprocess.html) |

Bundling pins the SQLite source and enabled capabilities within a build, making deployment more predictable than relying on a host library. SQLite documents the amalgamation as a single C implementation file designed for embedding. It does not make a cgo executable universally portable or guarantee every dependency is statically linked; target artifacts still need platform validation. [SQLite amalgamation](https://sqlite.org/amalgamation.html)

The measured build used SQLite 3.53.4 versus Python's 3.53.1, with Go 1.27.1 and Python 3.12.14. At 50,000 messages, broad-search medians were 39.49 ms for Python, 42.16 ms for embedded Go and 43.96 ms for the bridge; selective medians were 0.187, 0.194 and 0.631 ms. All 600 native comparisons matched Python's ordered IDs. These are implementation observations from `results/native/benchmark.json`, with uncontrolled caches, rotated method order and one serial run. They establish neither a language ranking nor production latency.

Nor does a dependency graph establish novelty: SQLite's documentation already demonstrates graph traversal, recursive CTEs and DAG ancestry. A new claim would need a clearly specified algorithm, appropriate prior-art comparison and independent evaluation. This benchmark tests retrieval and lifecycle overhead, not graph novelty or agent quality. [SQLite recursive graph queries](https://sqlite.org/lang_with.html#queries_against_a_graph)

Next experiments, in priority order:

1. **Control database differences.** Repeat with the same SQLite release, compile options, corpus/index bytes and SQL; record cache settings. Repeat randomized method orders and report variation. This separates library/build effects from host-language effects.
2. **Profile before rewriting.** Attribute time to SQLite execution, statement preparation, cgo crossings, row conversion, allocations and JSON transport. Use CPU/allocation profiles and, where necessary, native profiling for C frames. Go documents profiling and execution tracing tools. [Go diagnostics](https://go.dev/doc/diagnostics)
3. **Investigate broad-query work.** Test prepared-statement reuse and FTS5 `ORDER BY rank` plans against the current BM25 sort. SQLite documents potential rank-column sorting benefits, especially with LIMIT. Preserve the existing descending-ID tie break and exact ordered hits; adding that tie break may change the optimization opportunity. Inspect plans and measure rather than assuming equivalence implies speed. [FTS5 ranking](https://sqlite.org/fts5.html#sorting_by_auxiliary_function_results)
4. **Isolate transport and persistence.** Measure a no-op RPC and payload-size sweep, then compare batched search RPCs. Separately profile Begin and Commit with fixed history sizes and unchanged durability settings. Evaluate contention and recovery under concurrent callers before proposing lifecycle changes.

A Rust prototype becomes a justified experiment only after profiling identifies costs it could plausibly remove. It must preserve retrieval, persistence and recovery semantics and use the same benchmark protocol.
