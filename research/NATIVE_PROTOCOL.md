# Native benchmark protocol

This protocol is written before the first timing run. Run `python scripts/benchmark_native.py --help` for executable parameters. Build both Go commands with `go build -buildvcs=false` from `native/`.

The default search experiment creates fresh temporary SQLite databases at 1,000, 10,000 and 50,000 messages using Python TaskMemory, then copies each closed database for each method. Thus messages, IDs, timestamps and FTS index are identical. Each message contains one unique `markerNNNNNN` token plus the common terms `shared evidence benchmark corpus` and a deterministic group token. The 100 queries per size alternate 50 evenly spaced unique markers and 50 broad queries cycling through those four common terms. Every search ranks up to eight hits without task filtering. All exact ordered hit IDs are retained; agreement means entire ordered lists equal the Python result, not just overlapping sets.

Each method runs ten untimed searches (the first ten queries) and then one timed pass in the same alternating query order. Method order rotates by size: Python/Go/bridge, Go/bridge/Python, bridge/Python/Go. This reduces but does not eliminate order bias. File copying and corpus generation warm the OS page cache; cache state is uncontrolled, no cache flush occurs, and separate connections have separate SQLite page caches. This is a warm-process microbenchmark, not a cold-start or concurrent-load benchmark. SQLite library versions can differ and are reported. Query text is ASCII, so this does not test Unicode normalization parity.

Python timing uses `perf_counter_ns`; Go uses the monotonic component of `time.Now`/`time.Since`. Direct Python measures only TaskMemory.search; direct Go measures only Engine.Search, excluding command startup, output JSON, hit-ID extraction and corpus creation. Bridge timing includes NativeHarness.search, JSON request/reply encoding and parsing, stdio RPC and returned Python objects, with the server already running. No model is called. Warmup and measured calls are serial. No speed advantage is presumed.

The lifecycle experiment uses separate fresh empty databases for embedded Go and the bridge. Each creates one task outside timing, executes five untimed Begin+Commit warmups followed by 100 measured Begin+Commit operations. Every operation uses a unique request ID, fixed query `Record a benchmark acknowledgement`, fixed reply `Acknowledged.`, budget 2000, scope task, retrieval limit 24, recent 4 and estimated counting. Warmups remain in the database, so history grows identically from 10 through 210 messages. Timing covers both Begin and Commit, including persistence and context packing; bridge timing also includes two RPCs and Python session bookkeeping. It excludes task creation and process startup. There are zero model callbacks, inference calls, model-request records or tool calls. This measures lifecycle overhead, not a full agent task or quality.

Retain raw JSONL search and lifecycle rows, environment and final native database counts, and aggregate JSON/Markdown reports. Each aggregate reports n, median and empirical nearest-rank p95: sorted sample at 1-based index ceil(0.95*n), without interpolation. Search aggregates are split by corpus, method and query kind as well as combined. This is one local run with no confidence intervals; shared-machine noise, SQLite versions, storage and cache/order differences limit generalization. Actual counts and agreement must be reported even if results are unfavorable.
